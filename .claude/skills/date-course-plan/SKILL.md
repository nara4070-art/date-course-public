# 데이트 코스 플랜

사용자의 기분과 조건에 맞춰 **장소 + 먹거리를 시간순으로 엮은 코스**를 짠다. 사이트(데이트 코스 플래너)와 같은 기분·카테고리 체계를 써서, 플랜을 그대로 사이트 기록으로 옮길 수 있게 한다.

## 1. 조건 파악 — 되묻지 말고 추론

요청에서 아래를 뽑는다. 없는 값은 묻지 말고 합리적인 기본값으로 채운 뒤, 플랜 맨 위에 "가정한 조건"으로 한 줄 밝힌다. 사용자는 바로 쓸 수 있는 플랜을 원하고, 틀린 가정은 한 마디로 고칠 수 있기 때문이다.

| 항목 | 값 | 기본값 |
|---|---|---|
| 기분 | `tired` 피곤해요 · `excited` 설레요 · `active` 활동적이에요 · `calm` 조용히 쉬고 싶어요 · `refresh` 기분 전환이 필요해요 · `hungry` 맛있는 게 당겨요 | 말투에서 추론, 모르면 `refresh` |
| 날짜 | YYYY-MM-DD | 오늘. "이번 주말/토요일"은 오늘 이후 가장 가까운 토요일(오늘이 토요일이면 오늘). 요일은 달력으로 꼭 확인 |
| 지역 | 동네·역 이름 | 없음 → 일반 카테고리로 추천 |
| 예산 | 가볍게 / 적당히 / 특별한 날 | 적당히 (기념일이면 특별한 날) |
| 실내/야외 | 실내 / 야외 / 상관없음 | 날씨·계절 보고 판단, 비 오면 실내 |
| 시간대 | 낮 / 저녁·밤 / 하루 종일 | 오후~저녁 |

기분은 여러 개가 섞일 수 있다(예: 피곤한데 맛있는 건 먹고 싶다 → `tired` 위주에 `hungry` 먹거리). 사이트에 저장할 때는 가장 중심이 되는 기분 하나만 쓴다.

## 2. 후보 고르기

`references/catalog.md`에 사이트와 같은 장소 32개·먹거리 28개 카테고리가 기분/실내외/예산/시간대 태그와 함께 있다. 먼저 여기서 조건에 맞는 카테고리를 고른다.

**지역이 있으면** 웹 검색으로 그 지역의 실제 장소·가게를 1~2곳씩 찾아 카테고리에 붙인다(예: 🍜 뜨끈한 쌀국수 → "성수 ○○쌀국수"). 이름만 적고, 영업시간·가격처럼 확인 못 한 정보는 지어내지 말고 "가기 전 영업시간 확인"이라고 적는다. 그 지역에 딱 맞는 곳이 없으면 가장 비슷한 곳으로 바꾸고, 무엇이 다른지 한 줄 남긴다. 검색이 안 되면 카테고리만으로 짠다.

기분이 코스 전체의 강도를 정한다 (장소 수는 '메인으로 머무는 곳' 기준이다. 식사·카페와 이동 중 짧은 산책은 세지 않는다):
- `tired`/`calm`: 메인 장소 1~2곳, 이동 짧게, 앉아서 쉬는 곳 위주. 일정을 빡빡하게 넣지 않는 게 핵심이라, 빼도 되는 순서는 "힘들면 건너뛰기"라고 표시한다.
- `active`/`refresh`: 장소 2~3곳, 몸 쓰는 활동 하나 + 새로운 경험 하나.
- `excited`: 분위기(야경, 조명, 공연)를 마지막에 배치해 하루를 마무리한다.
- `hungry`: 먹거리 2~3개가 중심, 장소는 소화용 산책 정도.

## 3. 플랜 형식

```
## 💓 [제목 — 20자 안팎, 사이트 기록 제목으로 그대로 쓸 수 있게]
가정한 조건: 11/7(토) · 성수 · 적당히 · 실내 위주 · 오후~저녁   ← 사용자가 말한 건 굵게

| 시간 | 할 일 | 왜 |
|---|---|---|
| 14:00 | 🖼️ 미술관 · 전시회 — ○○갤러리 | 조용히 취향 나누며 시작 |
| 16:00 | 🍰 디저트 카페 — ○○ | 걷기 전 당 충전 |
| ... | ... | ... |

**동선**: 장소 간 이동 수단과 대략 시간 한 줄
**예상 비용**: 2인 기준 대략 범위. 확인한 가격이 없으면 "추정"이라고 밝히고 쓴다
**플랜 B**: 비 오거나 피곤해지면 바꿀 한 가지
참고: 확인 못 한 것(영업시간, 예약, 좌석 등) 1~3줄
출처: 웹 검색을 썼다면 링크 몇 개
```

마지막 줄에 사이트 저장 여부를 한 줄로 덧붙인다: "사이트에 이 코스를 기록할까요?" — 단, 사용자가 처음부터 "저장해줘/기록해줘"라고 했으면 묻지 말고 바로 4단계로 간다.

## 4. 사이트에 저장 (사용자가 원할 때만)

사이트는 모든 방문자가 하나의 기록을 공유하는 공개 서비스라서, 사용자가 원할 때만 쓴다.

- 주소: `https://date-course.neon-hyperdrive-worker.workers.dev`
- `POST /api/courses` (JSON). 응답 201에 저장된 기록(`id` 포함)이 온다.

```bash
curl -s -X POST https://date-course.neon-hyperdrive-worker.workers.dev/api/courses \
  -H "Content-Type: application/json" \
  -d '{"date":"2026-11-07","mood":"excited","title":"성수 전시 데이트","places":["🖼️ 미술관 · 전시회"],"foods":["🍰 디저트 카페","🍝 파스타 · 리조또"],"memo":"14:00 ○○갤러리 → 16:00 ○○ 카페 → 18:30 ○○ 파스타"}'
```

필드 규칙 (서버 검증과 같다 — 어기면 400과 한국어 에러가 온다):
- `date`: YYYY-MM-DD, 실제 있는 날짜
- `mood`: 위 표의 영어 키 하나 (사이트 화면이 이 키로 이모지를 그린다)
- `title`: 100자 이하
- `places`, `foods`: 문자열 배열, 각 100자 이하, 30개 이하. 사이트 화면과 맞도록 **catalog의 "이모지 이름" 형식 그대로** 넣는다. 실제 가게 이름은 memo에 쓴다.
- `places`와 `foods` 중 최소 하나는 있어야 한다
- `memo`: 2000자 이하. 시간표·가게 이름·동선을 한두 줄로 요약

저장 후에는 사이트 주소와 함께 "○월 ○일에 기록했어요"라고 알린다. 실패하면 서버 에러 메시지를 그대로 전하고 필드를 고쳐 한 번만 다시 시도한다.

같은 기간 기록을 보고 싶다는 요청이면 `GET /api/courses?from=YYYY-MM-DD&to=YYYY-MM-DD`로 읽어서 요약한다. 지난 기록과 겹치지 않게 추천하고 싶을 때도 이걸 쓰면 좋다.
